# 代码审查与迁移收口基线

## 目的

本文档用于接住旧 `legacy source: NeuroLoom代码审查清单.md` 这类“工程质量但不属于业务总线”的文档需求。

它当前回答的是：

1. 重构/迁移类工作应该如何做收口检查
2. 代码与文档如何一起审查
3. 什么情况算“可以进入下一轮”而不是“已经彻底完成”

---

## 1. 当前正式代码审查重点

### 1.1 边界是否变清楚

优先检查：

- owner 是否明确
- 目录是否按模块/实现线分层
- 是否还在把新逻辑继续堆进历史巨型文件

### 1.2 规则是否落库

优先检查：

- 新规则是否进入 `rules/`
- 新的最终定案是否进入 `docs/`
- 是否仍有关键规则只存在于聊天里
- canonical 文档树里的 markdown 引用是否仍指向真实存在的文件

### 1.3 运行时真相是否有证据

优先检查：

- 有没有构建/测试/回包/日志/输出目录证据
- 是否把“曾经成功一次”误写成“正式完成”

### 1.4 旧树是否还在误导

优先检查：

- 旧 `docs/` 是否仍与新树冲突
- 是否已经给出旧 -> 新的明确映射
- `docs/` / `rules/` 中的 markdown 引用是否仍指向真实存在的文件，而不是历史文件名残影
- tracked markdown 中是否还残留机器绑定绝对路径，而不是 repo-relative 或中性历史标签

---

## 2. 迁移类任务的收口标准

一轮迁移完成后，至少要回答：

1. 哪些旧内容已经被新树接管
2. 哪些还只是参考层
3. 哪些只属于历史过程
4. 新入口文档是否已经指向新的 canonical 文档

若回答不清，这轮迁移就还没收口。

---

## 3. 代码与文档必须同时收口

当前正式规则：

- 改目录结构，要改文档
- 改 owner，要改文档
- 改测试标准，要改文档
- 改部署主线，要改文档

不能接受：

- 代码改完了，但开发者仍只能从旧文档理解系统

## 5. 当前正式结论

从现在开始：

- 工程收口类检查有新的 canonical 文档
- 旧代码审查清单默认退为参考层
