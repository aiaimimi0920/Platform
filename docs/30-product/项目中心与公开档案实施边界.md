# 项目中心与公开档案实施边界

## 目的

本文档用于把旧 `legacy source: 项目中心模块化维护指南.md` 与 `legacy source: 用户档案模块化维护指南.md` 中关于项目中心、honor archive、公开档案的工程维护边界收口成新的专题。

---

## 1. 当前正式 owner 路径

### 1.1 项目中心

前端正式 owner：

- `web/src/features/account-project-center/`

### 1.2 用户档案 / honor archive

目标前端 owner：

- `web/src/features/account-honor/`

兼容层仍可保留在旧 `account-home/honor-*` 路径，但不应继续承载新主实现。

---

## 2. 当前正式后端边界

### 2.1 项目与投资记录

当前正式后端 owner：

- `account-domain honor-projects`

### 2.2 议题与投资议题

当前默认仍复用：

- `opinion-hub`

### 2.3 Agent showcase / 供给摘要

当前默认仍复用：

- `agent-registry`
- `agent-execution`

这意味着 honor/public profile 当前是：

- 展示与聚合层

不是：

- 再造第二套项目/议题/Agent 业务事实层

---

## 3. 当前正式产品边界

### 3.1 honor archive

继续负责：

- 摘要
- 展示配置
- 公开可见内容聚合

### 3.2 项目中心

负责：

- 项目列表
- 详情
- 视角切换
- 加入/赞助等动作

不得把完整项目中心重新塞回 honor 摘要卡。

---

## 4. 当前正式 operator 边界

项目、议题、Agent 的 operator 治理入口当前都应继续走各自正式的 operator 页面，而不是在 honor feature 里塞第二套管理 UI。

因此后续如需运维：

- 项目 -> 项目 owner/operator 入口
- 议题 -> 议题 operator 入口
- Agent -> Agent operator 入口

公开档案层只承接用户可见聚合，不承担平台治理主线。

---

## 5. 当前正式维护规则

后续若改项目中心或公开档案相关实现，默认检查：

1. 新逻辑是否进入对应 feature owner 路径
2. honor 摘要和项目中心是否重新混成一页
3. 是否误把 operator 功能塞回公开档案或 owner 终端

---

## 6. 当前正式结论

从现在开始，项目中心与公开档案的工程维护边界以本文为准；旧 `legacy source: 项目中心模块化维护指南.md` 与 `legacy source: 用户档案模块化维护指南.md` 继续保留为 source material，但不再作为新的主文档。
