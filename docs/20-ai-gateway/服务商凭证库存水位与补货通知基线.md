# 服务商凭证库存水位与补货通知基线

更新时间：2026-05-31

本文是 Rust `gateway` 对外公布“当前凭证是否够用、是否需要外部程序补货”的 canonical 规则。它服务于 EasyRegister、独立账号生成器、浏览器态凭证采集器、官方 API key 管理器等外部程序。

本文所有 `credential_count`、`token_window`、quota、额度窗口、水位和补货建议，描述的都是 **provider 真实凭证的供给侧库存 / 成本 / 上游额度口径**。它不等同于平台对终端用户的计费方式。

平台对用户可以采用完全不同的商业计费模型，例如：

- provider 真实凭证按 token 消耗或上游 quota 受限；
- 平台对用户按时间、套餐、席位、任务、订阅、包月、包年、无限调用权益或内部积分计费；
- provider 真实凭证按 5 小时 / 7 日 / daily quota 控制补货；
- 平台仍然可以把这些供给侧成本折算成用户侧的时间权益或套餐权益。

因此，本文的 canonical API 字段固定为 `providerSupplyMetricKind`，它只能回答“某类真实凭证是否够用、是否需要补货、建议补多少”，不能被解释为“用户应该如何计费”。历史字段 `metricKind` 仅作为兼容 alias 保留；DB 内部列名 `metric_kind` 也只是库存策略存储列，不代表用户侧 billing metric。

## 1. 目标

平台需要同时支持两类协作方式：

1. **信号通知（push）**：gateway 周期性统计某类凭证的库存水位；当可用量低于策略目标时，向 Redis Stream 写入补货信号。外部生成程序订阅后按缺口生产新凭证。
2. **调用式通知（pull）**：外部程序主动调用 gateway internal API 查询当前水位，判断是否需要补充、补多少、补哪一种凭证。

这两种方式使用同一套 DB policy 与同一套统计口径；push 只是 pull 结果中 `needsReplenishment=true` 的后台投递形式。

## 2. 真相层

凭证本体真相层仍然固定为：

- `gateway_provider_credentials`

库存策略与信号事件新增两张表：

- `gateway_credential_stock_policies`
- `gateway_credential_stock_signal_events`

这两张表不保存真实 secret，不替代 provider credential 本体，也不替代 `gateway_provider_credential_model_states` 的请求期健康状态。

## 3. 库存分类键

每一个需要被外部补货程序识别的凭证池，必须有一个稳定的 `stockClassKey`。

推荐格式：

```text
<serviceProviderKey>:<implementationLineKey>:<providerSurfaceKey>:<credentialMaterialKind>[:<tier-or-region>]
```

示例：

```text
chatgpt_platform:chatgpt_web_reverse:chatgpt_web_reverse:session_auth:free
qwen:qwen_official_api:qwen_dashscope_openai:api_key
suno_platform:web_reverse_api:suno:session_auth
udio_platform:web_reverse_api:udio:session_auth
lumalabs_platform:web_reverse_api:lumalabs:session_auth
```

策略还会显式保存：

| 字段 | 含义 |
| --- | --- |
| `serviceProviderKey` | 服务商身份，例如 `chatgpt_platform`、`qwen`、`suno`。 |
| `implementationLineKey` | 实现线，例如 `chatgpt_web_reverse`、`qwen_official_api`。 |
| `providerSurfaceKey` | 具体 surface / protocol profile，例如 `chatgpt_web_reverse`、`qwen_dashscope_openai`。 |
| `credentialMaterialKind` | 凭证材料类型，例如 `api_key`、`session_auth`、`browser_state`。`*` / `any` 可作为临时宽匹配。 |
| `providerAccountId` | 可选；如果绑定，则只统计该 provider account 下的凭证。 |
| `providerAdapter` | 可选；如果绑定，则只统计某 adapter。 |

上述 key 类字段在写入时会做 canonical normalization：去除首尾空白、大写转小写、非法字符折叠为 `_`。必填 key 以及非空可选 key 在 normalization 后不得为空；否则 gateway 返回 `400`，不会把错误的定向条件静默降级成宽匹配。

## 4. 可用凭证口径

v1 的 `usableCredentialCount` 只统计：

- `gateway_provider_credentials.archived_at is null`
- `gateway_provider_credentials.status = 'active'`
- provider account 匹配策略的服务商、surface、adapter、可选 account
- 若 `credentialMaterialKind` 不是 `*` / `any`，则 child credential payload 中的 `credentialMaterialKind` 必须匹配

不计入可用：

- `cooling`
- `disabled` / `inactive`
- `archived`
- 未知状态

后续可继续把 `gateway_provider_credential_model_states` 的模型级 `blocked / cooling / degraded` 纳入更细的 `model scoped stock`，但 v1 先以“凭证池补货”而不是“单模型补货”为中心。

## 5. 两类 provider 供给侧水位度量方式

### 5.1 按凭证数量度量

`providerSupplyMetricKind = credential_count`

字段：

| 字段 | 含义 |
| --- | --- |
| `minCredentialCount` | 低于该值为 `critical`，必须补货。 |
| `targetCredentialCount` | 低于该值为 `warning`，建议补到目标。 |
| `maxCredentialCount` | 高于该值为 `overstock`，不触发补货；`null` 表示无上限。 |

补货建议：

```text
suggestedCredentialTopUpCount = max(targetCredentialCount - usableCredentialCount, minCredentialCount - usableCredentialCount, 0)
```

### 5.2 按 provider token / quota 窗口度量

`providerSupplyMetricKind = token_window`

字段：

| 字段 | 含义 |
| --- | --- |
| `tokenWindowKey` | 窗口名，例如 `5h`、`7d`、`daily`。 |
| `tokenWindowSeconds` | 窗口秒数，例如 5 小时为 `18000`，7 天为 `604800`。 |
| `minAverageAvailableTokens` | 已知 token snapshot 的最低平均可用 token；低于该值为 `critical`。 |
| `targetAverageAvailableTokens` | 目标平均可用 token；低于该值为 `warning`。 |
| `targetCredentialCount` | token 统计之外的目标凭证数量下限。 |

`token_window` 策略不是替代数量水位，而是叠加 token 水位：只要数量水位或 token 水位任一侧需要补货，`needsReplenishment` 都会为 `true`；最终 `severity` 取两侧更严重的结果。

v1 会读取 provider credential 级 Redis quota snapshot：

```text
gw:provider-credential:quota:<providerCredentialId>
```

并尝试从 `rawData` 中识别：

- `remainingTokens`
- `remaining_tokens`
- `availableTokens`
- `available_tokens`
- `remaining`

如果 provider 的上游 quota 结构只能提供百分比，gateway 会尝试结合 `tokenLimit / totalTokens / limit` 推出估算剩余值。无法确认 token 的凭证会进入 `unknownTokenCredentialCount`，不会被伪造为 0。

## 6. Push 信号

后台任务由 Rust gateway worker 启动：

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `GATEWAY_CREDENTIAL_STOCK_MONITOR_ENABLED` | `true` | 是否启用库存水位后台扫描。 |
| `GATEWAY_CREDENTIAL_STOCK_MONITOR_INTERVAL_SECS` | `60` | 扫描间隔。 |

当某 policy 满足：

- `enabled = true`
- `signalEnabled = true`
- 当前统计 `needsReplenishment = true`
- 未被 `signalCooldownSecs` 抑制

gateway 会向 Redis Stream 写入事件。

默认 stream：

```text
gw:credential-stock:signals
```

事件名：

```text
gateway.credential_stock.replenishment_needed
```

payload 核心字段：

```json
{
  "eventType": "gateway.credential_stock.replenishment_needed",
  "stockClassKey": "chatgpt_platform:chatgpt_web_reverse:chatgpt_web_reverse:session_auth:free",
  "serviceProviderKey": "chatgpt_platform",
  "implementationLineKey": "chatgpt_web_reverse",
  "providerSurfaceKey": "chatgpt_web_reverse",
  "credentialMaterialKind": "session_auth",
  "providerSupplyMetricKind": "credential_count",
  "metricKind": "credential_count",
  "severity": "critical",
  "needsReplenishment": true,
  "usableCredentialCount": 2,
  "suggestedCredentialTopUpCount": 8,
  "signalKey": "credential_stock_signal_..."
}
```

`metricKind` 在信号 payload 中仅作为 legacy alias 暂时保留；新外部程序必须优先读取 `providerSupplyMetricKind`。

`signalKey` 用于去重和冷却；同一个 stock class、同一种 provider supply metric、同一个缺口 bucket 会得到稳定 key。

## 7. Pull API

所有 API 都是 internal management API，必须带 `GATEWAY_MANAGEMENT_TOKEN` 对应的：

- `x-management-token`
- 或 `Authorization: Bearer ...`

### 7.1 查询库存状态

```http
GET /v1/internal/gateway/credential-stock/status
```

可选 query：

- `stockClassKey`
- `serviceProviderKey`
- `implementationLineKey`
- `providerSurfaceKey`
- `credentialMaterialKind`
- `providerAccountId`
- `needsReplenishment`
- `limit`

返回：

```json
{
  "policies": [
    {
      "policy": {},
      "providerSupplyMetricKind": "credential_count",
      "metricKind": "credential_count",
      "usableCredentialCount": 2,
      "activeCredentialCount": 2,
      "coolingCredentialCount": 8,
      "countEvaluation": {},
      "tokenEvaluation": null,
      "needsReplenishment": true,
      "severity": "critical",
      "suggestedCredentialTopUpCount": 8,
      "signalKey": "credential_stock_signal_...",
      "signalPayload": {}
    }
  ],
  "summary": {
    "totalPolicyCount": 1,
    "enabledPolicyCount": 1,
    "needsReplenishmentPolicyCount": 1,
    "criticalPolicyCount": 1,
    "totalSuggestedCredentialTopUpCount": 8
  }
}
```

### 7.2 创建或更新 policy

```http
POST /v1/internal/gateway/credential-stock/policies
```

示例：

```json
{
  "stockClassKey": "chatgpt_platform:chatgpt_web_reverse:chatgpt_web_reverse:session_auth:free",
  "displayName": "ChatGPT Web Reverse Free Session Auth",
  "serviceProviderKey": "chatgpt_platform",
  "implementationLineKey": "chatgpt_web_reverse",
  "providerSurfaceKey": "chatgpt_web_reverse",
  "credentialMaterialKind": "session_auth",
  "providerAccountId": "optional-provider-account-id",
  "providerAdapter": "chatgpt_web_reverse_compatible",
  "providerSupplyMetricKind": "credential_count",
  "minCredentialCount": 5,
  "targetCredentialCount": 10,
  "maxCredentialCount": null,
  "signalEnabled": true,
  "signalStream": "gw:credential-stock:signals",
  "signalCooldownSecs": 300,
  "enabled": true
}
```

兼容期内，gateway 仍接受历史输入字段 `metricKind`，但新程序必须写入 `providerSupplyMetricKind`，避免把 provider 供给侧库存度量误读成用户侧计费方式。

为支持“GET 后原样 POST 更新”的外部程序，gateway 允许请求体同时带 `providerSupplyMetricKind` 与 legacy `metricKind`，前提是两者 normalization 后完全一致；若两者冲突，gateway 必须返回 `400`，不得静默选择其中一个。

### 7.3 手动触发信号扫描

```http
POST /v1/internal/gateway/credential-stock/signals/sweep
```

用途：

- 外部程序启动前主动触发一轮扫描
- 运维测试 push 链路是否可用
- CI / live lane 验证 policy 是否产生预期信号

## 8. 外部生成程序协作约定

外部程序应按以下顺序处理：

1. 启动时先调用 pull API 查询自己负责的 `stockClassKey`。
2. 如果 `needsReplenishment=true`，按 `suggestedCredentialTopUpCount` 生成或采集凭证。
3. 生成成功后通过 provider credential 导入 API 或 `~/.neuro` 文件夹同步写入单行凭证。
4. 常驻程序同时订阅 Redis Stream，收到同类 `stockClassKey` 信号后重复步骤 2-3。
5. 外部程序不得直接修改 `gateway_credential_stock_policies.lastSignal*`，去重与冷却由 gateway 负责。

## 9. 当前限制

- v1 不保证所有 provider 都能提供 token 窗口快照；没有 snapshot 时只输出 unknown，不伪造可用 token。
- v1 的 token 窗口不主动请求上游 quota；它读取已有 Redis quota snapshot，避免补货监控本身制造上游压力。
- v1 的可用凭证口径以 credential 行状态为主；模型级健康状态后续可以扩展为 `modelScoped=true` policy。
- Redis Stream 投递失败不会影响 gateway 用户请求，但会在 sweep 结果里体现 `redisErrorCount`。
